# RAG 知识库系统 - 初始脑暴

> 日期：2026-05-05
> 状态：脑暴阶段

## 1. 背景

用户有一批混合型非结构化文档（PDF、Word、Markdown、Excel、扫描件等），希望构建 RAG 知识库，供自建智能体检索和回答使用。

## 2. 核心原则

**不要把"文档"直接塞进向量库。** 应该做成一条清晰流水线：

```
原始文档 -> 解析/清洗 -> 结构化片段 -> 元数据 -> 向量索引 + 关键词索引 -> 检索编排 -> LLM回答
```

比"选哪个向量库"更重要的是三件事：
1. 解析质量
2. 切片策略
3. 元数据和检索策略

## 3. 文档分类处理

不要所有文件统一处理，至少分 4 类：

### A. 文本型文档
- markdown / txt / html / 网页导出 / docx 可直接提取文本的内容
- 直接抽文本，保留标题层级，按段落/小节切片

### B. 版面型文档
- PDF / 研报 / 合同 / 制度文档 / 带页码、表格、页眉页脚的文件
- 版面解析，去页眉页脚/重复水印/目录噪声，保留页码、章节、表格位置

### C. 扫描/OCR型文档
- 图片 PDF / 扫描件 / 截图文档
- OCR + 置信度打标，低置信度降权或提示

### D. 表格/半结构化文档
- Excel / CSV / 表格型附件
- 拆成：表说明 + 列定义 + 行级/分组摘要 + 关键指标卡片
- 不建议整表转长文本入库

## 4. 切片策略

### 原则
- 先按"语义结构"切（标题/章节/段落/列表/表格），再按长度补切
- chunk 大小：普通说明文档 400~800 字，上下文依赖强 200~500 字
- overlap：50~120 字
- 每个 chunk 保留"父级信息"（文档名/类型/标题路径/页码/时间/来源/版本/权限）

## 5. 混合检索

两套索引并行：
1. **向量索引**：语义相似、同义表达、自然语言提问
2. **关键词/BM25/全文索引**：专有名词、产品名、编号、日期、条款号

检索流程：
```
query -> query改写/意图识别 -> 向量召回topK + 关键词召回topK -> 合并去重 -> rerank -> 送LLM
```

## 6. Rerank

向量召回是"粗召回"，必须 rerank：
- 相关度
- 信息密度
- 来源可信度
- 时间新鲜度
- OCR 质量

## 7. 元数据设计

### 文档级
- doc_id / title / source_path / source_type / author
- created_at / updated_at / version
- business_domain / confidentiality_level / language

### chunk 级
- chunk_id / doc_id / section_path / page_no / chunk_index
- text / summary(可选) / keywords(可选)
- ocr_confidence(可选) / table_flag
- embedding_model / ingested_at

## 8. 表格专项处理

生成 3 层表示：
1. 表元信息（表名/来源/页码/时间范围/字段说明）
2. 表摘要（用途/关键指标/重要列）
3. 行/分组级片段（按产品/日期/分类拆分，保留列名+单位+上下文）

## 9. 回答编排层

1. 查询理解（找定义/事实/数值/版本差异/总结/流程）
2. 检索策略分流（专有名词->关键词优先，概念相似->向量优先，数值->表格索引优先）
3. 上下文组织（相关度/来源一致性/时间顺序/章节连续性）
4. 强制引用来源（文档名/页码/章节/时间版本）

## 10. 技术选型

### MVP 阶段
- 存储：本地目录 / OSS / MinIO
- 元数据：SQLite / PostgreSQL
- 向量库：pgvector / Chroma
- 全文检索：SQLite FTS / PostgreSQL 全文检索
- 解析：pymupdf / pdfplumber / python-docx / pandas / PaddleOCR

### 正式阶段
- 元数据：PostgreSQL
- 向量：pgvector / Milvus / Weaviate
- 关键词：OpenSearch / Elasticsearch
- 文档解析：版面解析服务化
- 队列：Celery / rq / Kafka
- 对象存储：MinIO / S3

**推荐组合：PostgreSQL + pgvector + OpenSearch + Python ingestion pipeline**

## 11. 落地路线

### 方案A：最小可用型
- 1 类核心文档，Python ingestion，PostgreSQL + pgvector，简单 BM25
- 快、成本低

### 方案B：效果优先型
- 版面解析 + OCR 质控，分类型切片，混合检索 + rerank，表格单独处理，评测集
- 准确率更高

### 方案C：企业治理型
- 文档生命周期管理，元数据规范，权限标签，增量更新，版本去重，可观测
- 长期最稳

## 12. 推荐起步顺序

1. 挑一个垂直文档域先跑通
2. 建最小 ingestion pipeline
3. 做混合检索
4. 做 20~50 条真实问题评测集
5. 再补 rerank / 版本 / 权限 / 表格增强

## 13. 质量判断标准

1. 召回对不对
2. 引用准不准
3. 答不出来时会不会乱编
4. 文档更新后能不能稳定同步

## 14. 最常见踩坑

1. 只关心向量库，不关心解析
2. 切片没有结构信息
3. 所有文档一种切法
4. 没有版本控制
5. 没有评测集
6. OCR 结果不打质量标
7. 直接让模型"根据召回内容自由发挥"而不加约束
